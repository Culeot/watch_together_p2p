## 模块划分

### 1. config.js - 全局配置

集中管理所有可配置参数：
- MQTT Broker 地址和连接选项
- STUN 服务器列表
- 视频参数（分辨率、帧率、码率）
- 屏幕共享画质档位
- 消息类型枚举

### 2. mqtt.js - MQTT 连接管理

封装 MQTT 客户端，提供：
- 自动重连
- 断线 will message
- 消息发布/订阅
- 消息处理器注册/移除
- 连接状态回调

### 3. webrtc.js - 连麦 WebRTC 管理

管理音视频 P2P 连接：
- 本地媒体流获取（getUserMedia）
- PeerConnection 创建和管理（Mesh 拓扑）
- 麦克风/摄像头开关控制
- VP9 编码偏好设置
- 移动端自动降级

### 4. screenshare.js - 屏幕共享 WebRTC 管理

独立于连麦的屏幕共享：
- 屏幕捕获（getDisplayMedia）
- 独立的 PeerConnection 管理
- 画质档位切换
- 码率限制（RTCRtpSender.setParameters）
- 动态画质降级（基于丢包率监控）

### 5. ui.js - UI 渲染和控制

管理所有页面元素：
- 首页（创建/加入房间）
- 会议室页面（主画面、连麦、控制面板）
- 弹窗、Toast、加载状态
- 响应式布局

### 6. app.js - 主入口

协调所有模块，实现：
- 房间创建/加入/离开
- 消息协议处理
- 管理员逻辑（踢人、批准共享、撤销共享）
- WebRTC 信令交换协调
- 异常处理（断线、房间满员等）

## 消息协议

所有消息通过 MQTT 主题 `watchtogether/{roomId}` 传输，格式为 JSON。

### 消息类型

#### 客户端 → 管理员

| 类型 | 说明 |
|------|------|
| `join-request` | 申请加入房间 |
| `leave` | 离开房间 |
| `webRTC-offer` | WebRTC 连麦 offer |
| `webRTC-answer` | WebRTC 连麦 answer |
| `webRTC-ice` | WebRTC ICE candidate |
| `screen-share-request` | 申请屏幕共享 |
| `screen-share-stop` | 停止屏幕共享 |
| `quality-change` | 画质变化通知 |

#### 管理员 → 所有客户端

| 类型 | 说明 |
|------|------|
| `room-created` | 房间已创建 |
| `join-approved` | 加入申请已批准 |
| `join-rejected` | 加入申请已拒绝 |
| `user-joined` | 新用户加入 |
| `user-left` | 用户离开 |
| `room-full` | 房间已满 |
| `screen-share-requested` | 有用户申请共享 |
| `screen-share-approved` | 共享申请已批准 |
| `screen-share-rejected` | 共享申请已拒绝 |
| `screen-share-started` | 共享已开始 |
| `screen-share-stopped` | 共享已停止 |
| `screen-share-revoked` | 共享被撤销 |
| `kicked` | 被踢出房间 |
| `admin-left` | 管理员离开，房间解散 |
| `error` | 错误消息 |

#### 屏幕共享 WebRTC 信令

| 类型 | 说明 |
|------|------|
| `webRTC-offer-screen` | 屏幕共享 offer |
| `webRTC-answer-screen` | 屏幕共享 answer |
| `webRTC-ice-screen` | 屏幕共享 ICE candidate |

## 网络拓扑

### Mesh 拓扑

本项目采用 **Mesh（网状）拓扑**：每个客户端与房间内所有其他客户端建立独立的 WebRTC PeerConnection。

```
    ┌─────┐
    │  A  │
    └──┬──┘
       │
   ┌───┼───┐
   │   │   │
   ▼   ▼   ▼
┌────┐┌────┐┌────┐
│ B  ││ C  ││ D  │
└────┘└────┘└────┘
```

**优点：**
- 无需中心媒体服务器
- 延迟最低（P2P 直连）
- 实现简单

**缺点：**
- 连接数 = n*(n-1)，n 为人数
- 6 人房间 = 30 个连接（每个方向 15 个）
- 上行带宽需求随人数增加

**适用场景：** ≤6 人的小房间，正好符合本项目的设计。

### 房间容量

- 最大 6 人同时在线
- 管理员 1 人 + 普通成员 5 人
- 超出后新成员收到 `room-full` 消息

## 性能优化

### 1. 码率控制

| 场景 | 分辨率 | 帧率 | 目标码率 | 上限码率 |
|------|--------|------|----------|----------|
| 连麦（桌面） | 1280×720 | 30fps | - | 1Mbps |
| 连麦（移动） | 640×360 | 24fps | - | 500Kbps |
| 屏幕共享 2K | 2560×1440 | 60fps | 8Mbps | 15Mbps |
| 屏幕共享 1080p60 | 1920×1080 | 60fps | 4Mbps | 8Mbps |
| 屏幕共享 1080p30 | 1920×1080 | 30fps | 2.5Mbps | 5Mbps |
| 屏幕共享 720p60 | 1280×720 | 60fps | 2Mbps | 4Mbps |

### 2. 动态画质降级

屏幕共享者持续监控丢包率：
- 每 3 秒检查一次
- 丢包率 > 5% 时自动降级
- 降级后 10 秒内不再降级（防止抖动）
- 降级顺序：2K60 → 1080p60 → 1080p30 → 720p60

### 3. 编码偏好

优先使用 VP9 编码（更好的压缩率），浏览器不支持时回退 VP8。

## 安全说明

### 已知限制

1. **MQTT Broker 消息未加密**：公共 EMQX Broker 上的消息是明文传输的。虽然 WebRTC 媒体流是端到端加密的，但信令消息（SDP、ICE）理论上可被第三方窃听。
2. **房间号可猜测**：6 位字母数字的房间号理论上可被暴力枚举。
3. **无身份验证**：任何人知道房间号即可加入（需管理员批准）。

### 使用建议

- 仅用于熟人之间的私密分享
- 不要用于传输高度敏感信息
- 房间号通过私密渠道分享（如微信、QQ）
- 发现可疑用户立即踢出
